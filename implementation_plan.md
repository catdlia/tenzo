# Глобальний план розробки гібридної архітектури Tenzo (PyTorch QAT + C++ MLIR Inference)

Цей план відображає скорегований архітектурний підхід: використання екосистеми PyTorch для тренування (QAT) та прямого експорту абстрактного графа (PyTorch FX), з подальшою оптимізацією та виконанням у C++ рушії Tenzo (через MLIR) для задач інференсу.

## User Review Required

> [!WARNING]
> Перевірте, чи відповідає цей розподіл обов'язків вашому баченню продукту на найближчі місяці.
> Зверніть особливу увагу на Фазу 2 (формат серіалізації ваг), оскільки це архітектурно вплине на те, як рушій керує оперативною пам'яттю.

## Open Questions

> [!IMPORTANT]
> 1. Як ми будемо зберігати здамплені ваги з PyTorch? Прямо зараз найкращий варіант для інференсу — це сирий бінарний файл (`.bin`), який C++ рушій мапитиме в пам'ять через `mmap()`, щоб не копіювати їх. Чи підходить такий підхід?
> 2. Чи є вже готова реалізація `autograd.Function` для Straight-Through Estimator в PyTorch, чи це перше завдання, яке треба зробити з нуля?

## Фаза 1: PyTorch ML-Frontend (Навчання та QAT)
PyTorch бере на себе всю математику диференціювання, оптимізаторів та підготовки ваг.

1. **Імплементація STE (Straight-Through Estimator)**
   - Написання кастомних `autograd.Function` у Python для пропускання градієнтів під час зворотного проходу крізь операції заокруглення.
2. **Універсальні QAT-шари**
   - Розробка базових модулів (наприклад, `BitLinear`, `BitAttention`), які підтримують параметризацію: `bit_width` (2, 4, 8) та `scheme` (ternary, symmetric).
3. **Тренування / Дистиляція**
   - Побудова тренувального циклу в Python, де модель "заморожується" (folding) після фіне-тюнінгу (ваги фіксуються вже у квантованому вигляді).

---

## Фаза 2: The Bridge (PyTorch FX -> MLIR Експортер)
Створення "моста" для передачі топології та ваг від Python до C++ без зайвої бюрократії (відмова від ONNX).

1. **FX Graph Tracer**
   - Використання `torch.fx.symbolic_trace` для захоплення плоского графа (Abstract Syntax Tree) "замороженої" QAT-моделі.
2. **MLIR Emitter (Транслятор)**
   - Написання Python-класу (Visitor), який мапить вузли FX у специфічні операції діалекту `TenzoOps` (наприклад, переклад `torch.add` $\rightarrow$ `tenzo.add`, або виклик кастомного шару $\rightarrow$ `tenzo.quantize`).
3. **Серіалізація ваг (Zero-Copy Export)**
   - Скрипт-експортер записує всі масиви ваг у неперервний бінарний файл (`weights.bin`), а в `model.mlir` генерує лише offset/strides-казівники на них. Це дозволить Tenzo миттєво піднімати ваги через `mmap`.

## Фаза 3: C++ MLIR Backend (Розширення Tenzo)
Адаптація компілятора під динамічну маршрутизацію та універсальне квантування.

### `src/dialect/TenzoOps.td`
- **[NEW] Параметричні операції квантування:**
  Додати `tenzo.quantize` та `tenzo.dequantize` з атрибутами `bit_width` та `quant_scheme`. Замість хардкодингу 1.58-bit, ми даємо можливість планувальнику вибирати мікроядра залежно від параметрів.
- **[NEW] Високорівневі абстракції:**
  Додати плейсхолдери `tenzo.attention` та `tenzo.kv_cache` для подальшої оптимізації контексту.

### `src/passes/LinalgLowering.cpp`
- **[MODIFY] Зниження нових операцій:**
  Прописати правила lowering для нових нод `tenzo.quantize` та `tenzo.dequantize` у стандартний `linalg.generic`. Це дозволить тестувати граф і переглядати базовий код від LLVM ще до написання агресивних кастомних мікроядер.

### `src/runtime/MemRefUtils.h`
- **[MODIFY] C++ Рантайм:**
  Додати функціонал для створення "view" над пам'яттю (кастомні масиви `strides` у `MemRefDescriptor`), що стане базою для `Implicit Shuffle` (маршрутизація без копіювання `transpose`).

### `src/passes/PackingKernels.cpp`
- **[MODIFY] Підтримка AffineMap для пакування:**
  Додати підтримку `AffineMap` у генератори пакування (`generatePackBFunction` / `generatePackAFunction`). Без цього `vector.transfer_read` не зможе зчитувати дані з урахуванням нових страйдів, і статична маршрутизація (Implicit Shuffle) не запрацює.

## Фаза 4: Екстремальні оптимізації (Zero-Copy & Fused Packing)
Після стабілізації "моста" імплементується ядро ідеї обходу Memory Wall.

### Апаратні профілі та Автотюнінг (`src/context/X86HardwareProfile.cpp` та `AutoTuner.h`)
- **[MODIFY] Конфігурація тайлінгу (Вивільнення регістрів):**
  Зменшення тайлінгу мікроядра з `MR=6, NR=16` до `MR=4, NR=8` або `4x16`. Це робиться не хардкодом у pass, а через `X86HardwareProfile.cpp` (та інші профілі), щоб архітектура залишалася гнучкою і звільнила ~6 YMM регістрів для уникнення Register Spilling'у при побітових операціях.
- **[NEW] Розширення автотюнера:**
  Додати в існуючий автотюнер підтримку пошуку ідеальних значень `MR`/`NR` для специфічних комбінацій операцій (наприклад, звичайний MatMul vs. 1.58-bit MatMul), щоб автоматично адаптуватися під будь-яку цільову архітектуру.

### `src/passes/ExplicitMicroKernelPass.cpp`
- **[MODIFY] Диспетчеризація Мікроядер:**
  Впровадження маршрутизатора в pass:
  - Якщо `bit_width == 8` $\rightarrow$ стандартне AVX2 мікроядро.
  - Якщо `bit_width == 2` $\rightarrow$ виклик нового `FusedTernaryKernel`.

### `src/passes/FusedTernaryKernelPass.cpp` (Новий файл)
- **[NEW] 1.58-bit Fused Kernel (Запис кешу):**
  Написання злитого ядра для KV-Cache: проєкція (MatMul) $\rightarrow$ квантизація $\rightarrow$ стиснення (Bit-Packing 4 тернарних значень в 1 байт) — без вивантаження проміжних результатів у RAM.
- **[NEW] Обчислення Уваги (Читання кешу):**
  Написання спеціалізованого ядра для обчислення $Q \times K^T$ на вже спакованих даних. Замість повільних FMA-інструкцій використовуватимуться швидкі SIMD-інструкції (побітові зсуви, логічне АБО, popcount) для екстремально швидкого множення.
